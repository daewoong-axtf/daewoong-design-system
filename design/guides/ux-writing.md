# UX 라이팅 가이드

> 화면 문구의 말투·용어와 버튼·오류·빈 상태·토스트·알림 문구 규칙을 정한다.
>
> 기본안이다. 서비스 성격에 맞게 고쳐 쓴다.

## 1. 보이스앤톤

**친근한 격려 + 정확한 안내.**

- 일반 사용자에게는 따뜻하게, 운영자에게는 명확하게 쓴다.
- 존댓말을 기본으로 한다. 호칭이 필요하면 "OO님"을 쓴다.
- 이모지는 쓰지 않거나 성공·경고에 1개 이내로 쓴다.
- 비난하거나 사과하지 않는다. 해결책을 제시한다.

## 2. 어미

컴포넌트별로 어미를 맞춘다. 한 표면 안에서 섞지 않는다.

| 표면 | 어미 | 예 |
| --- | --- | --- |
| [Toast](../components/toast.md) | 해요체 과거형 | 주문을 저장했어요 |
| [Callout](../components/callout.md) | 해요체 | 02:00~04:00에는 접속할 수 없어요. |
| [Alert Dialog](../components/alert-dialog.md) | 해요체, 제목은 질문형 | 게시글을 삭제할까요? / 삭제하면 되돌릴 수 없어요. |
| [Empty State](../components/empty-state.md) | 해요체 | 검색 결과가 없어요 |
| [Field](../components/field.md) 설명·오류 | "~하세요" | 8자 이상 입력하세요 |
| 이메일·메신저 알림 | 해요체 | 주문이 확정되었어요. |

- 부탁은 "~해주세요"로 붙여 쓴다.
- 문어체 "~하였습니다"는 쓰지 않는다.
- **처리 결과는 능동형으로 쓴다.** 서비스가 한 일을 그대로 말하면 짧고 분명하다.

| 쓰지 않는다 | 쓴다 |
| --- | --- |
| 저장되었어요 · 삭제되었어요 · 등록되었어요 | 저장했어요 · 삭제했어요 · 등록했어요 |
| 신청하였습니다 | 신청했어요 |

- **서비스가 하지 않은 일은 피동으로 쓴다.** 폼 되돌림("{대상} 수정이 취소되었어요"), 시간이 지나 생긴 일("세션이 만료되었어요"), 대상이 곧 행위인 "로그아웃되었어요"가 그렇다.
- 소개 콘텐츠처럼 UI 문구가 아닌 글에는 이 규칙을 적용하지 않는다.

## 3. 버튼 라벨

- 구체적인 동사로 쓴다. 예: "주문 확정", "문서 승인", "회원 등록".
- "확인", "제출", "OK"만 쓰지 않는다. 결정이 필요 없는 1버튼 알림은 "확인"을 쓸 수 있다.
- 파괴적 행동은 결과를 드러낸다. 예: "주문 취소", "삭제".
- 한 줄에 들어가게 쓴다. 길면 문구를 줄인다([Button](../components/button.md)).

## 4. 상태 용어

같은 개념에는 한 용어만 쓴다. 서비스마다 상태 표를 하나 정하고 그 표 밖의 표현을 쓰지 않는다. 주문을 예로 들면 다음과 같다.

| 상태 | 라벨 | 의미 |
| --- | --- | --- |
| `pending` | 승인 대기 | 신청 후 확정 전 |
| `confirmed` | 확정 | 주문 확정 |
| `cancelled` | 취소 | 반려되었거나 취소됨 |
| `completed` | 완료 | 처리 종료 |

"대기중", "확정됨"처럼 비슷한 표현을 섞지 않는다.

## 5. 오류 메시지

**무엇이·왜 + 해결책**을 쓴다.

- **Do** "이미 등록된 이메일이에요. 다른 이메일을 입력해주세요."
- **Do** "재고가 모두 소진됐어요. 수량을 줄이거나 다른 상품을 선택해주세요."
- **Don't** "오류가 발생했습니다."
- **Don't** "잘못 입력하셨습니다."

입력값 오류는 [Field](../components/field.md)에 문제와 고치는 방법을 함께 쓴다(예: "8자 이상 입력하세요").

경고 팝업은 결과를 밝힌다. 예: "출고 뒤에 취소하면 배송비가 청구돼요. 취소할까요?"

## 6. 빈 상태

[Empty State](../components/empty-state.md)는 무엇이 없는지(Title), 왜·어떻게(Description), 다음 행동(Action)으로 쓴다.

- 다음 행동을 안내한다. 예: "아직 문서가 없어요" / "첫 문서를 만들어볼까요?"
- 불러오기 실패는 원인과 재시도를 쓴다. 예: "불러오지 못했어요" / "네트워크를 확인하고 다시 시도해주세요." + `다시 시도`
- "데이터가 없습니다"처럼 시스템 말투로 쓰지 않는다.
- **문의를 유도할 때는 창구를 구체적으로 밝힌다.** "관리자에게 문의해주세요"처럼 받는 곳이 불분명한 표현 대신 실제 창구를 적는다. 예: "쿠폰이 필요해요. {문의 창구}로 문의해주세요."
- **화면이 판단한 기준을 그대로 쓴다.** 사용 가능 여부로 걸러낸 화면이면 "보유한"이 아니라 "사용 가능한"으로 쓴다. 만료분까지 있는 것처럼 읽히면 안내가 사실과 어긋난다.
  - **Do** "사용 가능한 쿠폰이 없어요"
  - **Don't** "보유한 쿠폰이 없어요"

## 7. 숫자·정보 표현

| 항목 | 표현 |
| --- | --- |
| 남은 양 | 잔여 8개 |
| 현재 / 전체 | 참석 3명 / 정원 8명 |
| 시간 | 24시간제 10:00 |
| 소요 시간 | 25분 |
| 날짜 | 2026년 5월 20일 (수) |
| 금액 | ₩550,000 |

포맷 세부는 [content-i18n.md](content-i18n.md)를 따른다.

## 8. 알림 문구

이메일·메신저 알림은 무슨 일이 언제 일어났는지 첫 문장에 쓴다.

| 상황 | 예 |
| --- | --- |
| 확정 | OO님, 5월 20일 10:00 주문이 확정되었어요. |
| 사전 안내 | 내일 10:00 회의가 있어요. 잊지 마세요. |
| 설문 | 서비스는 어떠셨나요? 만족도 조사에 참여해주세요. (1분 소요) |

## 9. 토스트

방금 한 행동의 결과를 알리는 한 문장이다. [Toast](../components/toast.md) 명세를 따르고, 타이밍은 [interaction.md 5장](interaction.md#5-피드백)을 따른다.

| 상황 | 문구 | variant |
| --- | --- | --- |
| 저장·등록·수정·삭제 성공 | {대상}을/를 저장했어요 | `positive` |
| 취소 처리 성공 | {대상}을/를 취소했어요 | `positive` |
| 모달 닫기(변경 있음) | {대상} 수정이 취소되었어요 | `default` |
| 모달 닫기(변경 없음) | 토스트 없음 | — |
| 섹션 인라인 수정 취소(변경 있음) | {섹션 라벨} 수정이 취소되었어요 | `default` |
| 섹션 인라인 수정 취소(변경 없음) | 토스트 없음 | — |
| 작업 실패 | {대상}을/를 저장하지 못했어요 + Action `다시 시도` | `critical` |
| 권한 없는 페이지에서 기본 화면으로 이동 | 요청한 페이지는 접근 권한이 없어 기본 화면으로 이동했어요 | `default` |

- **대상을 생략하지 않는다.** 토스트는 모달이 닫힌 뒤 홀로 남으므로 대상이 없으면 무엇이 처리됐는지 알 수 없다. 대상이 곧 행위인 경우만 예외다("로그아웃되었어요").
- **대상은 하나다.** 입력 필드가 여러 개여도 저장 버튼 하나로 저장되면 대상은 그 화면이 다루는 대상 하나다. 필드명을 나열하지 않는다.
- **같은 화면의 토스트는 대상명을 맞춘다.** 대상은 화면 맥락에서 가장 짧게 통하는 이름으로 고른다.
- **행위를 뜻하는 말은 뺀다.** 섹션명 "회원 관리"는 "회원을 저장했어요"로 쓴다.
- **"완료" 단독으로 쓰지 않는다.** 결과를 구체적으로 쓴다.
- **문장 끝에 마침표를 찍지 않는다.** 토스트는 한 문장이다.
- **긴 원인을 넣지 않는다.** 긴 설명이 필요하면 [Callout](../components/callout.md)을 쓴다.
- **서버가 사유와 함께 거절하면 토스트가 아니다.** [Alert Dialog](../components/alert-dialog.md) 제목에 "{대상}을/를 취소할 수 없어요", 본문에 서버 사유를 쓴다.
- **취소와 되돌림을 구분한다.** 되돌릴 수 없는 "주문을 취소했어요"와 폼을 닫았을 뿐인 "주문 수정이 취소되었어요"는 문장이 달라야 한다.

## 10. 연결 상태 문구

서버에 도달하지 못할 때 전역 안내에 쓰는 표준 문구다. 동작은 [interaction.md 15장](interaction.md#15-전역-연결-상태)을 따른다.

| 환경 | 문구 |
| --- | --- |
| 개발·스테이징 | 개발 서버에 연결할 수 없어요. 사내망이나 VPN에 연결되어 있는지 확인해주세요. |
| 운영 | 서버에 연결할 수 없어요. 잠시 후 다시 시도해주세요. |

- 재시도 라벨은 "다시 시도"다.
- 로그인 화면에서는 폼 안에도 같은 문구를 보인다. "아이디 또는 비밀번호가 일치하지 않아요"와 혼동되지 않게 네트워크 원인임을 분명히 쓴다.
- 타임아웃도 같은 문구로 묶는다. 사용자에게는 똑같이 연결이 안 되는 상황이다.

## 11. Do / Don't

- **Do** 구체적인 동사로 버튼 라벨을 쓴다.
- **Do** 오류 메시지에 해결책을 쓴다.
- **Do** 빈 상태에 다음 행동을 제시한다.
- **Do** 서비스의 상태 용어를 하나로 통일한다.
- **Do** 변경이 있는 취소에만 취소 토스트를 띄운다.
- **Do** 서버 도달 불가는 원인과 재시도를 안내한다.
- **Don't** "확인", "제출"만 쓰지 않는다.
- **Don't** 비난·사과조로 쓰지 않는다.
- **Don't** 이모지·느낌표를 많이 쓰지 않는다.
- **Don't** 같은 개념에 다른 용어를 섞지 않는다.
- **Don't** 네트워크 단절을 "오류가 발생했습니다"로 뭉뚱그리거나 인증 실패 문구와 섞지 않는다.
